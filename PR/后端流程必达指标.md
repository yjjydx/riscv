# PR 后端流程必达指标

本文根据 `PR/step1.init.tcl` 到 `PR/step6.chipfinish.tcl` 的实际脚本整理，目标是回答：每个后端流程必须完成什么指标，才算这一关基本过了。

## 总体原则

- 前面阶段更关注“结构正确、约束正确、物理可实现”
- 中间阶段更关注“布局/时钟/布线是否收敛”
- 最后阶段更关注“版图交付物是否完整、可检查、可导出”
- `setup/hold`、`DRV`、`DRC`、`connectivity`、`antenna` 不是同一类问题，要分开看
- `utilization` 和 `congestion` 是物理实现质量的重要指标，不能只看时序和 DRC
- 严格 signoff 还要关注 `LVS`、寄生参数提取、IR drop、EM、串扰/SI 和功耗

## 联网核对后补充的 signoff 项

公开资料里常把最终后端收敛描述为：布线完成后继续做最终时序、物理检查和交付文件导出。OpenROAD Flow Scripts 的教程中，报告目录包含 congestion、DRC、设计统计和 antenna log；OpenLANE 论文也提到 DRC/LVS、antenna、寄生参数提取和最终 STA；Cadence 公开资料则把 timing、area、power、signal integrity、manufacturing，以及 IR drop/EM 等作为实现和签核关注点。

结合我们当前脚本，需要区分两类：

- 当前脚本已经覆盖：`timeDesign`、`verify_drc`、`verifyConnectivity`、`verifyProcessAntenna`、`streamOut`、`saveNetlist`、`defOut`、`write_sdc`、`write_lef_abstract`
- 当前脚本未完整覆盖但最终 signoff 应关注：`LVS`、`SPEF/寄生提取`、`IR drop`、`EM`、更完整的功耗分析、串扰/SI 分析

### 为什么这些不能漏

- `LVS`：确认 GDS 版图抽出来的连接关系和网表一致。DRC clean 不代表 LVS 一定 clean。
- `SPEF/寄生提取`：route 后金属线有真实 RC，最终 STA 应尽量基于提取后的寄生参数。
- `IR drop`：确认电源网络供电不会局部掉压太多，否则时序和功能都可能受影响。
- `EM`：确认金属线电流密度不过高，避免长期可靠性问题。
- `SI/crosstalk`：确认相邻金属线耦合不会让时序或信号噪声失控。

## 利用率和拥塞怎么判断

### 利用率

利用率可以简单理解为：core 区域里已经被标准单元、macro、blockage 占了多少。

一般经验：

- `60% ~ 75%`：比较健康，后续优化和 ECO 空间较充足
- `75% ~ 80%`：偏紧，需要重点关注拥塞、时序和 DRV
- `80%` 以上：风险较高，尤其是 macro 多、pin 多、布线层少的设计

推荐用 `dbGet` 手工计算，避免不同 Innovus 版本命令不兼容：

```tcl
set core_box [dbGet top.fPlan.coreBox]
set llx [lindex $core_box 0]
set lly [lindex $core_box 1]
set urx [lindex $core_box 2]
set ury [lindex $core_box 3]
set core_area [expr {($urx - $llx) * ($ury - $lly)}]

set inst_area 0
foreach area [dbGet top.insts.cell.area] {
  set inst_area [expr {$inst_area + $area}]
}

set util [expr {$inst_area / $core_area * 100.0}]
puts "Core area = $core_area"
puts "Instance area = $inst_area"
puts "Utilization = $util %"
```

如果这段命令在某些库上统计到 macro/physical-only cell，结果会偏保守。更严谨时可以分别统计 standard cell、macro、blockage，再结合 GUI density map 一起判断。

### 拥塞

拥塞可以简单理解为：某个区域想经过的线太多，但可用布线资源不够。

判断时重点看：

- 是否有 overflow
- 是否有大面积 congestion hotspot
- 热点是否集中在 macro 周围、pin 附近、bus 区域或高扇出网络附近

你当前 Innovus 环境里 `reportCongestion` 也不是有效命令，因此不要把它作为固定检查命令。

更稳妥的判断方式：

- 在 GUI 中打开 congestion/density 相关视图，看是否有大面积红色热点
- 查看 `place_opt_design`、`routeDesign` 日志里是否有 overflow、congestion、routing resource 不足等信息
- route 后结合 `verify_drc`、`verifyConnectivity` 和 `reportWire -summary` 判断是否因为拥塞导致绕线异常
- 如果 route 阶段反复绕线失败、线长暴涨、局部 DRC 很多，也说明前面 placement/floorplan 的拥塞需要重新处理

### 线长

线长可以辅助判断布局是否合理。线长太长，往往会带来更大的电容、更差的 transition 和更差的 setup。

判断命令：

```tcl
reportWire -summary ../report/place_opt/wirelength.rpt
```

### 它们之间的关系

- 利用率高，不一定立刻失败，但会压缩 route 和 ECO 空间
- 拥塞严重，route 可能绕远路，导致线长、电容和 transition 变差
- 线长变长，setup 和 DRV 都可能被拖差
- 没有 DRC 不代表没有拥塞，只能说明工具最终绕出了一版满足规则的线
