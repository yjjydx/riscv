# 常用调式命令

本文档用于汇总 Innovus 后端流程里常用的调试命令，重点覆盖我们前面已经用到的几个命令。后续如果新增新的调试命令，可以继续按相同格式补充。

## 1. 使用原则

- 这些命令主要用于定位时序、DRV、单元驱动能力、负载、过渡时间等问题。
- 不同阶段能做的事情不同，`place`、`CTS`、`route` 阶段看到的问题和修法也不完全一样。
- 一般推荐流程是：先定位问题对象，再查看 timing/DRV 细节，再尝试局部修复，最后重新检查报告。

---

## 2. 常用命令总览

| 命令 | 主要作用 | 常见使用场景 |
| --- | --- | --- |
| `ecoChangeCell` | 替换实例所使用的标准单元型号 | 驱动太弱、slew 太差、想手工升级门尺寸 |
| `refinePlace` | 增量合法化布局 | 换单元、插单元、局部 ECO 后重新整理布局 |
| `timeDesign` | 重新做时序/DRV 分析并输出报告 | 看 setup/hold/DRV 是否改善 |
| `report_constraint` | 汇总约束违例 | 查 max_transition、max_capacitance、fanout 等 DRV |
| `get_pins` | 获取 pin 对象 | 给 `report_timing`、`all_fanin` 等命令提供对象 |
| `report_timing` | 查看具体路径的时序细节 | 分析最差路径、查 slew/cap/load/net delay |
| `dbGet` 计算利用率 | 查看面积利用率 | 判断 core 是否太满、是否容易拥塞 |
| GUI/日志检查拥塞 | 查看布线拥塞 | 判断局部区域是否 routing resource 不够 |
| `reportWire` | 查看线长统计 | 判断布局是否导致线长过长、绕线压力过大 |

## 3. 逐条命令说明

### 3.1 `ecoChangeCell`

#### 作用

将某个实例从当前标准单元替换为另一个等价逻辑但驱动能力不同的单元，常用于手工修复局部问题。

典型用途：

- 某级门驱动太弱，导致 `max_transition` 很差
- 想把 `ND2D1` 升级为 `ND2D2`、`ND2D4`
- 局部路径 setup 很紧，希望提升驱动能力

#### 常见写法

```tcl
ecoChangeCell -inst U_MUX_3to1_LMD/FE_RC_139_0 -cell ND2D2
```

#### 参数解释

- `-inst`：要修改的实例名
- `-cell`：替换成的新标准单元

#### 典型场景

原来单元是 `ND2D1`，驱动输出很慢，slew 达到 `1.6ns`，可以尝试升级到 `ND2D2` 或更大驱动型号。

#### 注意事项

- 替换前要确认逻辑功能兼容，不能随便把逻辑不同的门替换掉。
- 替换后通常要执行 `refinePlace`。
- 替换后建议重新执行 `timeDesign` 和 `report_constraint` 检查结果。
- 单元变大后可能带来面积、功耗、拥塞变化。

---

### 3.2 `refinePlace`

#### 作用

对当前设计做增量布局调整和合法化，确保修改后的单元位置、重叠、行对齐等满足布局要求。

#### 常见写法

```tcl
refinePlace
```

#### 典型用途

- `ecoChangeCell` 后让工具重新整理局部布局
- 插入 tie cell、buffer、inverter 后进行合法化
- 做完小规模 ECO 后不想重新完整 place

#### 你可以把它理解为

不是“从头重新布局”，而是“对刚才的局部修改做收尾整理”。

#### 注意事项

- `refinePlace` 主要是增量调整，不是全面优化。
- 它不会自动帮你完整修完所有时序问题。
- 执行后再看报告，才知道改动是否真的有效。

---

### 3.3 `timeDesign`

#### 作用

执行时序分析，并根据选项输出路径、DRV、slack 等报告。

#### 常见写法

```tcl
timeDesign -postCTS -pathReports -drvReports -slackReports -numPaths 50 -prefix test_nd2_resize -outDir ../report/postCTS
```

#### 常见阶段写法

```tcl
timeDesign -preCTS -idealClock
timeDesign -postCTS
timeDesign -postRoute
```

#### 常见参数解释

- `-preCTS`：在 CTS 前分析，时钟通常按 ideal clock 看
- `-postCTS`：在 CTS 后分析，时钟树已经建立
- `-postRoute`：在布线后分析，结果更接近最终真实情况
- `-idealClock`：按理想时钟分析
- `-pathReports`：输出路径报告
- `-drvReports`：输出 DRV 报告
- `-slackReports`：输出 slack 报告
- `-numPaths 50`：输出 50 条路径
- `-prefix`：报告名前缀
- `-outDir`：报告输出目录

#### 生成的 `.gz` 文件怎么查看

`timeDesign` 经常会把报告压缩成 `.gz` 文件，这是正常现象，不是报错。

你这条命令执行后，常见会生成下面几类文件：

- `test_nd2_resize.summary.gz`：汇总结果，建议优先看
- `test_nd2_resize.tran.gz`：transition 相关违例
- `test_nd2_resize.cap.gz`：capacitance 相关违例
- `test_nd2_resize.slk` 或 `*.slack*.gz`：slack 相关结果
- `test_nd2_resize.tarpt.gz`：时序路径报告

#### 推荐查看顺序

1. 先看 `summary.gz`，快速判断整体 setup/hold/DRV 情况
2. 再看 `tran.gz`，确认最差 `max_transition`
3. 如果要深挖具体路径，再看 `tarpt.gz`

#### Linux 系统下面怎么查看

在 Linux 服务器上，最常用的有 3 种方式：

1. 直接查看压缩内容，不解压
2. 先解压，再查看文本
3. 配合 `grep` 过滤关键字

#### 命令行查看方法

直接查看，不解压原文件：

```bash
zcat ../report/postCTS/test_nd2_resize.summary.gz
```

分页查看，更适合长报告：

```bash
zless test_nd2_resize.summary.gz
```

或：

```bash
zcat test_nd2_resize.summary.gz | less
```

如果想先解压再看：

```bash
gunzip test_nd2_resize.summary.gz
```

解压后会得到：

```text
test_nd2_resize.summary
```

然后可以再用：

```bash
less test_nd2_resize.summary
```

#### 查关键内容的常见方法

比如只想找 `slack`、`transition`、`violations` 这些关键字，可以这样：

```bash
zcat test_nd2_resize.summary.gz | grep -i slack
zcat test_nd2_resize.tran.gz | grep -i violation
zcat test_nd2_resize.tran.gz | grep -i transition
```

如果报告很长，这种方式会比全文翻看更高效。

#### 更适合你的实际做法

因为这些报告本质上都是文本，最推荐这样看：

1. 先用 `zless test_nd2_resize.summary.gz` 打开
2. 找 `setup`、`hold`、`DRV` 总体统计
3. 再用 `zless test_nd2_resize.tran.gz` 打开
4. 找最差 violator、required transition、actual transition、slack
5. 最后结合 `report_timing` 去看具体路径

#### 结合我们当前调试场景怎么用

如果你现在是在查 `ND2D1 -> ND2D2` 替换后的效果，建议重点看：

- `summary.gz`：确认整体是否变好
- `tran.gz`：确认最差 slew 是否下降
- `tarpt.gz`：确认对应路径的 timing 是否改善

#### 主要看什么

- setup/hold slack
- max transition
- max capacitance
- max fanout
- 最差路径是否改善

#### 注意事项

- `slack` 为正，不代表 DRV 一定没问题。
- `DRV` 很差，也不一定立刻造成 setup fail，但说明设计质量不健康。
- 不同阶段报告结果会变化，`postRoute` 通常最真实。

### 3.4 `report_constraint`

#### 作用

查看约束违例，尤其适合看 DRV 类型问题。

#### 常见写法

```tcl
report_constraint -drv_violation_type max_transition -all_violators
```

#### 其他常见写法

```tcl
report_constraint -drv_violation_type max_capacitance -all_violators
report_constraint -drv_violation_type max_fanout -all_violators
```

#### 参数解释

- `-drv_violation_type max_transition`：查看最大过渡时间违例
- `-drv_violation_type max_capacitance`：查看最大电容违例
- `-drv_violation_type max_fanout`：查看最大扇出违例
- `-all_violators`：列出所有 violator

#### 适合做什么

- 找出当前最差的 tran/cap/fanout 违例
- 修完单元后重新对比违例是否变少
- 判断工具到底有没有把最差点修掉

#### 注意事项

- 这类报告偏“约束检查”，不是完整路径时序分析。
- 想看某个违例为什么发生，通常还要配合 `report_timing` 一起看。

---

### 3.5 `get_pins`

#### 作用

获取设计里的 pin 对象。很多分析命令需要的是“对象”而不是纯字符串，`get_pins` 就是桥梁。

#### 常见写法

```tcl
get_pins U_RF/FE_OCPC347_WD_1/I
```

#### 常见配合写法

```tcl
report_timing -to [get_pins U_RF/FE_OCPC347_WD_1/I]
```

#### 适合做什么

- 指定某个终点 pin 做 timing 分析
- 查某个具体 pin 是否存在
- 作为其他命令的输入对象

#### 注意事项

- 层级名必须写对，否则可能返回空对象。
- 如果名字很长，建议先确认实例名和 pin 名是否准确。

---

### 3.6 `report_timing`

#### 作用

查看具体时序路径的详细信息，是定位路径问题最核心的命令之一。

#### 常见写法

```tcl
report_timing -to [get_pins U_RF/FE_OCPC347_WD_1/I]
```

#### 常见分析目标

- 看某条路径的起点、终点
- 看每级单元和网络延迟
- 看哪个门的 slew 特别差
- 看负载是否过大
- 看 setup/hold slack 到底卡在哪一级

#### 常配合的问题

- 为什么这里的 transition 这么大
- 为什么 setup 是正的，但 DRV 还是很差
- 为什么工具没有自动修这里

#### 看报告时重点关注

- endpoint / beginpoint
- data arrival time
- required time
- slack
- 某一级 pin 的 transition
- 某段 net 的 delay 和 load

#### 注意事项

- `report_timing` 看到的是“路径视角”。
- `report_constraint` 看到的是“违例汇总视角”。
- 两者要结合起来看，才容易判断问题根因。

### 3.7 用 `dbGet` 计算利用率

#### 作用

查看当前设计的面积利用率，也就是标准单元、macro、blockage 等占用了 core 区域多少空间。

它主要用于判断：

- core 是否设得太小
- 标准单元是否摆得太满
- 后续 route 是否容易拥塞
- 是否需要扩大 core、降低利用率、调整 macro 或 blockage

#### 常见写法

```tcl
set core_box [dbGet top.fPlan.coreBox]
set llx [lindex $core_box 0]
set lly [lindex $core_box 1]
set urx [lindex $core_box 2]
set ury [lindex $core_box 3]
set core_area [expr {($urx - $llx) * ($ury - $lly)}]

set inst_area 0
foreach area [dbGet top.insts.cell.area] {
  set inst_area [expr {$inst_area + $area}]
}

set util [expr {$inst_area / $core_area * 100.0}]
puts "Core area = $core_area"
puts "Instance area = $inst_area"
puts "Utilization = $util %"
```

如果想保存到报告文件，可以把上面命令放进一个 Tcl 文件，例如 `area.tcl`，然后在 Innovus 里执行：

```tcl
source area.tcl
```

#### 主要看什么

- core area：core 总面积
- instance area：标准单元和宏单元面积
- utilization：利用率，通常用 `instance area / core area * 100%` 计算
- placeable area：真正可放标准单元的面积

#### 注意

你当前 Innovus 环境里 `reportUtilization` 会报：

```text
invalid command name "reportUtilization"
```

所以不要再使用 `reportUtilization`。更稳妥的方式是用 `dbGet` 读取 core box 和 instance area 后自己计算。

#### 怎么判断

利用率不是越高越好。  
利用率太低，面积浪费；利用率太高，place/route 容易拥塞，setup/DRV 也更难修。

一般经验：

- `60% ~ 75%`：通常比较健康，比较容易收敛
- `75% ~ 80%`：偏紧，需要关注拥塞和时序
- `80%` 以上：风险较高，尤其 macro 多、pin 多、布线层少时更容易出问题

这些不是绝对标准，要结合工艺、设计规模、macro 数量、布线层数量一起判断。

#### 常见问题

如果利用率太高，后续可能出现：

- `place` 阶段单元挤在一起
- `route` 阶段绕线资源不够
- `max_transition`、`max_capacitance` 更难修
- hold/setup ECO 没有空间插 buffer

### 3.8 检查拥塞

#### 作用

查看布局或布线阶段的拥塞情况。拥塞可以理解为：某个局部区域需要通过的线太多，但可用布线资源不够。

#### 推荐查看方式

你当前 Innovus 环境里 `reportCongestion` 不是有效命令，所以不要再使用它。

更稳妥的检查方式：

- 用 GUI 打开 congestion map 或 density map，看是否有大面积红色/深色热点
- 看 `place_opt_design` 的日志和报告，是否提示 congestion 或 overflow
- 看 `routeDesign` 的日志，是否出现 routing overflow、routing resource 不足、反复 reroute
- route 后结合 `verify_drc`、`verifyConnectivity` 和 `reportWire -summary` 判断是否因拥塞导致绕线异常

#### 主要看什么

- overflow：布线需求超过资源的程度
- hotspot：拥塞热点区域
- horizontal / vertical congestion：水平/垂直方向拥塞
- congestion map：GUI 中红色或深色区域通常代表拥塞更严重

#### 怎么判断

- 没有 overflow：最理想
- 少量局部 overflow：可以继续观察，后续 route 可能修掉
- 大面积 overflow：需要认真处理，可能要回到 floorplan/place 调整

#### 常见原因

- core 利用率太高
- macro 摆放太近，形成 routing channel 太窄
- pin 都挤在一侧，局部线网过密
- blockage 设置太多
- high fanout net 或 bus 集中经过同一区域

#### 常见修法

- 降低 core utilization
- 扩大 core 或增加 macro 间距
- 调整 pin/macro 位置
- 增加 placement padding
- 改善 path group 或高扇出网络 buffer 策略

---

### 3.9 `reportWire`

#### 作用

查看线长统计，辅助判断布局质量。线长过长通常意味着单元相距太远，可能导致 delay、transition、capacitance 变差。

#### 常见写法

```tcl
reportWire -summary ../report/place_opt/wirelength.rpt
```

#### 主要看什么

- 总线长是否异常偏大
- 长线数量是否过多
- 布局优化前后线长是否明显改善

#### 和拥塞/利用率的关系

- 利用率太高，单元可能被挤压，绕线更曲折
- 拥塞严重时，route 会绕远路，线长增加
- 线长增加后，cap 和 transition 也可能变差

## 4. 一个常见调试流程

下面是我们前面实际遇到的 `max_transition` 调试思路：

1. 先用 `report_constraint -drv_violation_type max_transition -all_violators` 找最差违例。
2. 记录最差 pin 或最差实例位置。
3. 用 `get_pins` 获取该 pin。
4. 用 `report_timing -to [get_pins ...]` 查看该路径细节。
5. 判断是不是某级门太弱、负载太大、扇出太高、路径太长。
6. 如果确认是门太弱，可用 `ecoChangeCell` 升级单元。
7. 执行 `refinePlace` 做局部合法化。
8. 再执行 `timeDesign` 重新分析。
9. 再执行 `report_constraint` 检查违例是否下降。

### 4.1 Post-CTS DRV 四批局部修复记录

本节记录本项目在 CTS 完成并执行 post-CTS 优化后，对数据网络 `max_transition` 和 `max_capacitance` 进行的四批局部 cell resize。该方法只适用于已经确认是驱动能力不足或输出负载过大的数据网络，不应直接套用到 clock tree 或逻辑功能不同的 cell。

#### 初始结果

```text
Setup WNS          : +0.007 ns
max_cap            : 16 nets，Worst=-0.059
max_transition     : 29 nets，Worst=-1.299
```

报告中的 `/ZN`、`/Z` 通常是驱动端，`/I`、`/A1`、`/B2` 等通常是接收端。同一条网可能同时报告驱动端和接收端，因此不要按 term 数量逐个替换接收 cell，应先找到对应的输出驱动器。

#### 每批修复前的准备

先保存当前数据库，确保可以回退：

```tcl
saveDesign ../database/riscv.cts_drv_eco_before_batchN.enc
```

查询实例当前使用的 cell：

```tcl
dbGet [dbGet top.insts.name <instance_name> -p].cell.name
```

查询同系列可用驱动版本：

```tcl
dbGet [dbGet head.libCells.name <cell_pattern> -p].name
```

每批都使用下面的安全替换循环。只有当前 cell 与预期旧 cell 一致时才执行替换，避免重复运行脚本后误改实例：

```tcl
foreach item $resize_plan {
  lassign $item inst old_cell new_cell
  set current_cell [dbGet [dbGet top.insts.name $inst -p].cell.name]

  if {$current_cell eq $old_cell} {
    puts "RESIZE: $inst : $old_cell -> $new_cell"
    ecoChangeCell -inst $inst -cell $new_cell
  } else {
    puts "SKIP: $inst current=$current_cell expected=$old_cell"
  }
}

# 当前仍处于正式 route 前，只做布局合法化，不执行 ecoRoute。
refinePlace
```

#### Batch 1：修复最差的三个 MUX 数据驱动器

```tcl
set resize_plan {
  {U_MUX_3to1_LMD/FE_RC_139_0 ND2D1   ND2D4}
  {U_MUX_3to1_LMD/FE_RC_142_0 CKND2D0 CKND2D2}
  {U_MUX_3to1_LMD/FE_RC_9_0   IND3D2  IND3D4}
}
```

选择依据：这三个输出同时出现在最差 max-transition 和 max-capacitance 报告中，先在同逻辑系列内提高驱动能力。

#### Batch 2：继续修复 MUX 区域的 inverter、clock-NAND 和 AOI 驱动器

```tcl
set resize_plan {
  {U_MUX_3to1_LMD/FE_RC_705_0 INVD1      INVD4}
  {U_MUX_3to1_LMD/FE_RC_555_0 INVD1      INVD4}
  {U_MUX_3to1_LMD/FE_RC_561_0 CKND1      CKND4}
  {U_MUX_3to1_LMD/FE_RC_831_0 AOI211XD2  AOI211XD4}
  {U_MUX_3to1_LMD/FE_RC_943_0 AOI211XD2  AOI211XD4}
}
```

#### Batch 3：修复 RF、ALU、PC 和另一组 MUX 数据驱动器

```tcl
set resize_plan {
  {U_RF/FE_RC_594_0              INR4D1   INR4D4}
  {U_RF/U70                      NR2D1    NR2D4}
  {U_ALU/FE_RC_112_0             INR2D1   INR2D4}
  {U_PC/U12                      MUX2D0   MUX2D2}
  {U_PC/U9                       MUX2D0   MUX2D2}
  {U_MUX_3to1_B/FE_RC_18_0       AOI22D0  AOI22D2}
  {U_RF/U178                     NR2XD0   NR2XD2}
  {U_MUX_3to1_B/U46              AOI22D0  AOI22D2}
}
```

#### Batch 4：最后一批仍有升级空间的弱驱动器

```tcl
set resize_plan {
  {U_RF/U181          NR2D1    NR2D4}
  {U_RF/FE_RC_1161_0  ND4D0    ND4D4}
  {U_RF/U127          NR2XD1   NR2XD4}
  {U_RF/U129          NR2XD1   NR2XD4}
  {U_ALU/FE_RC_53_0   AOI22D0  AOI22D2}
  {U_RF/U146          NR2D2    NR2D4}
}
```

Batch 4 后停止继续批量放大 cell。剩余违例中部分驱动器已经是该逻辑系列最大驱动，继续 resize 只会增加面积和上游输入电容，应改为分析完整 timing path、降低接收端输入电容、插入 buffer，或交给 route/post-route 优化。

#### 每批完成后的检查

重新分析 setup 和 DRV：

```tcl
timeDesign -postCTS -pathReports -drvReports -slackReports \
  -numPaths 50 -prefix drv_eco_batchN -outDir ../report/postCTS
```

重新分析 hold：

```tcl
timeDesign -postCTS -hold -pathReports -slackReports \
  -numPaths 50 -prefix drv_eco_batchN_hold -outDir ../report/postCTS
```

查看剩余 DRV：

```tcl
report_constraint -drv_violation_type max_transition -all_violators
report_constraint -drv_violation_type max_capacitance -all_violators
```

确认结果正常后保存该批数据库：

```tcl
saveDesign ../database/riscv.cts_drv_eco_batchN.enc
```

#### 四批修复效果

| 阶段 | Setup WNS (ns) | max-cap nets | max-cap Worst | max-tran nets | max-tran Worst |
| --- | ---: | ---: | ---: | ---: | ---: |
| 初始 | +0.007 | 16 | -0.059 | 29 | -1.299 |
| Batch 1 | +0.007 | 14 | -0.050 | 29 | -0.932 |
| Batch 2 | +0.007 | 9 | -0.017 | 26 | -0.732 |
| Batch 3 | +0.009 | 1 | -0.001 | 19 | -0.336 |
| Batch 4 | +0.026 | 1 | -0.001 | 13 | -0.336 |

四批修复后，max-cap 基本清零，max-transition 的数量和最差值明显下降，setup WNS 没有恶化并有所提高。

#### 本次 hold 报告的特殊情况

本次 `timeDesign -postCTS -hold` 中的 85 条违例全部属于：

```text
rst -> reset buffer -> register/CDN
```

它们是异步复位释放的 removal check，不是上述 MUX/RF 数据 cell resize 造成的普通数据 hold。处理这类问题时应检查 reset 的同步释放结构和 SDC 约束，不要为了让报告变绿而直接对 `rst` 添加未经验证的 false path。

#### 为什么 DRV 报告不能直接给出修法

`report_constraint` 只能报告违例 pin 的 Required、Actual 和 Slack。例如它会指出 `FE_RC_9_0/ZN` 与接收端 `/I` 的 transition 超限，但不会自动说明是驱动器太弱、接收端输入电容过大还是长线造成。

需要结合 `report_timing` 中的逐级信息判断：

```text
Cell / Fanout / Load / Slew / Delay / Physical Location
```

本项目后续发现 `FE_RC_9_0` 已是最大驱动 `IND3D4`，其下一级 `INVD4` 输出负载很小但输入电容较大。这类情况更适合尝试将接收端 `INVD4` 降为 `INVD2`，或评估插 buffer，而不是继续放大已经到顶的前级驱动器。

## 5. 拥塞和利用率的常见调试流程

如果怀疑设计太挤，建议按下面顺序查：

1. 先用 `dbGet` 面积脚本看整体利用率。
2. 再用 GUI congestion/density map 看局部是否有 congestion hotspot。
3. 查看 place/route 日志，看是否出现 overflow 或 routing resource 不足。
4. 如果拥塞集中在 macro 周围，优先检查 macro 间距和 channel 宽度。
5. 如果拥塞集中在 IO pin 附近，优先检查 pin 分布是否太集中。
6. 如果拥塞集中在标准单元密集区，考虑降低 utilization 或增加 padding。
7. 最后结合 `reportWire` 看线长是否异常。

#### 判断思路

利用率是“core 里放了多少东西”。  
拥塞是“这些东西之间的线够不够走”。  
线长是“信号为了连接或绕开拥塞走了多远”。

这三个要一起看，不能只看其中一个。

## 6. 几个常见理解误区

### 误区 1：`slack` 为正就说明没问题

不是。  
`slack` 只说明 setup/hold 可能过了，但 `max_transition`、`max_capacitance`、`max_fanout` 仍可能严重违例。

### 误区 2：工具没修，说明这里不用修

也不一定。  
工具可能是在 setup、DRV、面积、功耗之间做了折中，不代表这个点一定“没问题”。

### 误区 3：`refinePlace` 会自动做完整优化

不会。  
它更多是局部调整和合法化，不等于重新完整优化整版设计。

### 误区 4：CTS 阶段不能动逻辑单元

不绝对。  
如果是很局部的标准单元驱动问题，CTS 后也可以做小规模 ECO 修复，但修完后要重新检查时序和 DRV。

### 误区 5：利用率越高越好

不是。  
利用率高可以节省面积，但会让 placement、route、ECO 修复空间变少。利用率过高时，时序、DRV、拥塞都会更难收敛。

### 误区 6：没有 DRC 就说明不拥塞

不是。  
DRC 是规则检查，拥塞是资源压力。一个设计可以没有 DRC，但仍然有局部拥塞，只是工具暂时绕线成功了。

## 7. 联网核对后补充的 signoff 调试项

除了前面这些 Innovus 内部常用命令，最终后端收敛还会关注一些更偏 signoff 的检查项。它们不一定都由当前脚本直接完成，但答辩或项目验收时最好知道。

| 项目 | 主要看什么 | 常见阶段 |
| --- | --- | --- |
| LVS | 版图抽取出来的连接是否和网表一致 | GDS 导出后 |
| 寄生参数/SPEF | route 后真实金属线 RC，用于更准确 STA | route/chip finish 后 |
| IR drop | 电源网络是否局部掉压过大 | power signoff |
| EM | 金属线电流密度是否超可靠性限制 | power signoff |
| power | dynamic/leakage/internal power 是否合理 | place 后、route 后、signoff |
| crosstalk/SI | 相邻金属线耦合是否影响时序或信号质量 | route 后 |

### 7.1 LVS

LVS 是 Layout Versus Schematic，也就是比较“版图”和“网表”是否等价。

初学者理解：

- `DRC` 看的是版图形状合不合工艺规则
- `LVS` 看的是版图连接关系和原始网表是不是同一个电路

所以没有 DRC 不代表 LVS 一定通过。LVS 通常需要 Pegasus、Calibre、Netgen 等工具配合 GDS、netlist、rule deck 来做。

### 7.2 寄生参数和 SPEF

route 后金属线不再是理想连线，而是有电阻、电容。寄生参数提取就是把这些 RC 提出来，常见输出是 SPEF。

为什么重要：

- pre-route 的时序主要靠估算线长
- post-route 的时序应该尽量基于真实 RC
- SPEF 越准确，最终 STA 越接近真实芯片

如果后续有 signoff STA，通常会用网表、SDC、Liberty、SPEF 一起分析。

### 7.3 IR drop 和 EM

IR drop 是电源网络上的电压下降。电流经过有电阻的金属线时，局部 VDD 会比理想值低。

EM 是 electromigration，电迁移。它关注金属线长期承受电流后是否可靠。

为什么重要：

- IR drop 太大，会让 cell 变慢，setup 可能恶化
- EM 过大，可能造成长期可靠性风险
- decap、power ring、power stripe、PG mesh 都和这类问题有关

### 7.4 Power 和 SI

Power 一般看：

- dynamic power
- leakage power
- internal power
- clock power

SI/crosstalk 一般看：

- 相邻线之间的耦合噪声
- crosstalk 对 delay 的影响
- 高速总线、长线、拥塞区域是否更容易出问题

在我们当前脚本里，route 阶段已经开启了：

```tcl
setNanoRouteMode -routeWithSiDriven true
```

这说明布线时已经让工具考虑 SI，但最终是否满足更严格的 SI signoff，仍然需要看对应报告或 signoff 工具结果。

## 8. PrimeTime（PT）正规分析流程

PrimeTime 的职责是读取最终实现结果，进行独立的静态时序分析（STA）。它通常不负责布局布线，也不会直接修改 Innovus 数据库。发现问题后，应回到 Innovus 做 ECO，再重新导出网表和寄生参数，最后重新运行 PT。

### 8.1 总体流程

```text
Innovus 完成 route/chip finish
        ↓
冻结并导出最终门级网表、SDC、DEF
        ↓
StarRC/Quantus/Calibre xRC 提取寄生 RC
        ↓
生成与最终网表匹配的 SPEF
        ↓
PT 读取网表、时序库、SDC、SPEF
        ↓
检查 link、约束覆盖率和寄生标注率
        ↓
分别进行 setup/hold 多角分析
        ↓
报告 timing、DRV、unconstrained path、coverage
        ↓
如有问题：Innovus ECO → 重新布线 → 重新提取 SPEF → 再跑 PT
```

### 8.2 第一步：冻结并导出最终实现数据

必须确保网表、SDC、DEF 来自同一次最终 PR 数据库，不能把不同日期、不同 ECO 版本的文件混用。

| 文件 | 典型文件名 | 生成位置/工具 | 用途 |
| --- | --- | --- | --- |
| 最终门级网表 | `riscv.vg` | Innovus `saveNetlist` | PT 读取 CTS、ECO 后的真实逻辑结构 |
| 最终约束 | `riscv_post_pr.sdc` | Innovus `write_sdc` | 提供时钟、IO delay、false path、multicycle path 等约束 |
| 最终 DEF | `riscv.def` | Innovus `defOut -routing` | 给 StarRC 提供器件位置和实际布线几何信息 |
| GDS | `riscv.gds2` | Innovus `streamOut` | 主要用于 DRC/LVS；采用 DEF 提取的 StarRC 流程通常不直接读取它 |

检查 DEF 的顶层设计名：

```bash
grep -m1 "^DESIGN " /path/to/riscv.def
```

应看到：

```text
DESIGN riscv ;
```

### 8.3 第二步：提取寄生参数

寄生提取通常由 StarRC、Quantus 或 Calibre xRC 独立完成。PT 本身只读取提取结果，不负责从 DEF/GDS 生成 RC。

以当前 StarRC DEF-based 流程为例，提取阶段需要：

| 文件 | 作用 |
| --- | --- |
| 最终 `riscv.def` | 提供标准单元、Macro、金属线和通孔几何信息 |
| Tech LEF | 描述工艺层、via、布线层等抽象信息 |
| SRAM LEF | 描述 `TS1N65LPLL2048X64M8` 的尺寸、pin 和 obstruction |
| `def_starrc.map` | 把 DEF 中的 `M1`～`M9`、via 名映射到 StarRC 工艺层名 |
| `starrcxt.nxtgrd` | StarRC RC 工艺模型，必须与实际金属栈匹配 |
| `starrc.cmd` | 指定顶层、输入文件、输出 SPEF 和提取选项 |

主要输出：

| 输出 | 作用 |
| --- | --- |
| `riscv_core_*.spef` | PT 使用的电阻、电容及耦合电容 |
| `starrc.sum` | StarRC 运行汇总和消息统计 |
| `starrc_work/`、`*.gpd` | StarRC 中间数据库，不是 PT 的主要输入 |

必须检查 SPEF 的更新时间晚于或等于最终 DEF，并检查 StarRC 是否报告 open、short、missing layer 或 unresolved cell。

### 8.4 第三步：运行 `pt.tcl`

寄生参数提取完成后，后续读取网表、链接时序库、读取 SDC/SPEF、设置 propagated clock 和 OCV、检查约束、分析 setup/hold、输出报告等步骤，都可以统一写在 `pt.tcl` 中执行。

运行 PT 前只需确认 `pt.tcl` 中以下输入路径正确，并且网表、SDC、DEF、SPEF 来自同一次最终 PR 结果：

| PT 输入 | 作用 |
| --- | --- |
| `riscv.vg` | CTS、ECO 和 route 后的最终门级网表 |
| `riscv_post_pr.sdc` | 最终时序约束 |
| 标准单元 `.db` | 标准单元时序模型 |
| SRAM `.db` | SRAM 时序模型 |
| `riscv_core_*.spef` | StarRC 提取的互连寄生 RC |
| `pt.tcl` | 完成 PT 读取、分析和报告输出 |

进入脚本所在目录后运行：

```bash
pt_shell -f pt.tcl | tee pt.log
```

具体 PT 命令直接查看 `pt.tcl`。运行结束后重点查看：

- `check_timing` 是否存在未约束路径、无时钟端点或 unresolved reference；
- `report_annotated_parasitics` 是否存在大量未标注网络；
- setup/hold 的 WNS、TNS 和违例路径数；
- max transition、max capacitance、max fanout；
- analysis coverage 和 SI/crosstalk 报告。

### 8.5 第四步：根据 PT 结果进行 ECO

如果 PT 发现违例，应回到 Innovus 完成 ECO，然后重新导出网表和 DEF、重新提取 SPEF、再次运行 `pt.tcl`：

```text
PT 定位问题 → Innovus ECO/ecoRoute → 重新导出 → StarRC 重提 SPEF → 重跑 pt.tcl
```

只要发生 cell 替换、buffer 插入、器件移动或重新布线，旧 SPEF 就不能继续作为最终分析数据。

### 8.6 学姐当前 PT 流程做得正确的部分

从现有 `pt.tcl` 可以看出，它已经包含以下有效步骤：

- 读取布局布线后的 `riscv.vg`；
- 同时链接标准单元和 SRAM `.db`；
- 读取 StarRC 生成的 SPEF，并保留 coupling capacitance；
- 开启 SI 分析；
- 读取后端 SDC并设置 propagated clock；
- 设置 derate 和 clock uncertainty；
- 运行 `check_timing`；
- 检查 `report_annotated_parasitics`；
- 输出 setup/hold、DRV、analysis coverage 和分类时序报告；
- 使用 `save_session` 保存 PT 会话。

因此这套脚本能够正常跑出 PT 报告，整体框架适合作为教学和调试流程。

### 8.7 学姐当前 PT 流程存在的问题

#### 问题 1：Setup 和 Hold 使用了同一套慢角库

脚本链接了类似：

```text
标准单元：tcbn65lpwc.db
SRAM：ss1p08v125c.db
```

这属于慢角/worst-case 方向。之后仅通过：

```tcl
report_timing -delay_type max
report_timing -delay_type min
```

分别报告 setup 和 hold，并不会自动把 hold 切换到快角库。因此：

- setup 报告具有一定参考价值；
- hold 报告并不是严格意义上的快角 hold signoff；
- 正规流程应给 hold 配置 fast/min 标准单元库和 SRAM 库，或使用 `set_min_library`。

#### 问题 2：只有一个 `typical` SPEF

脚本读取：

```text
riscv_core_typical.spef
```

没有体现 RC max、RC min 等寄生角。教学分析可以先使用一个典型 SPEF，但完整 signoff 应根据工艺要求分别分析合适的 RC corner。

#### 问题 3：StarRC 工艺栈与当前 GDS/DRC 配置存在潜在不一致

当前 GDS 导出 map 使用 `9M_6X2Z`，Calibre DRC rule deck 使用 `1p9m_6X2Z0U`，但学姐 StarRC 配置采用：

```text
1p9m_6X1Z1U/starrcxt.nxtgrd
```

顶层金属厚度组合不同，会影响金属电阻和电容。用该 SPEF 可以验证流程、观察大体趋势，但不能宣称为严格匹配工艺的 signoff 结果。

#### 问题 4：文件路径和版本容易混用

目前出现过 `PT_FLOW`、`PT_test`、`PR_test`、`PR_ydx` 等不同目录。如果 PT 读取的网表来自一个 PR 目录，而 StarRC 的 DEF 来自另一个目录，就会导致寄生参数错配。

运行前必须记录并核对：

```text
门级网表路径和时间
SDC 路径和时间
DEF 路径和时间
SPEF 路径和时间
标准单元/SRAM 库角
StarRC RC 工艺模型
```

#### 问题 5：旧 SPEF 可能已经过期

之前检查到旧 `riscv_core_typical.spef` 的时间早于后续修改的 `starrc.cmd` 和 `def_starrc.map`。如果最终 PR 又进行了 CTS、ECO 或 route，旧 SPEF 更不可能代表当前版图，必须重新生成。

#### 问题 6：Hold 的 variation 建模不完整

脚本主要设置了：

```tcl
set_timing_derate -late ...
```

但没有看到与 hold 对应的完整 early/min derate、快角库和 RC min 组合。因此 `-delay_type min` 只能要求 PT 报告最短路径，不能替代完整 hold corner 建模。

#### 问题 7：SPEF 后仍设置 wire-load mode

脚本包含：

```tcl
set auto_wire_load_selection false
set_wire_load_mode top
```

对已经正确标注 SPEF 的 post-layout 网络，wire-load model 通常没有必要。它可能掩盖未标注网络问题。更正规的做法是检查并解决 `not annotated` 网络，而不是依赖 wire-load model。

### 8.8 对当前项目的建议

当前可以分两级使用这套流程：

1. **流程验证/比赛调试**：沿用学姐的 StarRC 和 PT 脚本，重新生成与当前 DEF 匹配的 SPEF，并明确记录 `6X1Z1U` 工艺模型不完全匹配。
2. **严格 signoff**：补齐 `6X2Z0U` 对应的 RC tech model、快角标准单元/SRAM 库、RC max/min 场景，并分别运行 setup/hold。

无论采用哪一级，最低要求都是：`riscv.vg`、SDC、DEF 和 SPEF 必须来自同一版最终实现结果，并确认寄生标注覆盖率没有大面积缺失。
